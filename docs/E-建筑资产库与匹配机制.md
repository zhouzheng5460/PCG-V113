# 建筑：匹配 vs 参数化，以及资产库方案

> 起因：想知道 Placemaker 是不是"按位置匹配合适尺寸的预设"，同类型不同尺寸地块会不会长出不同建筑，以及我们能否先做资产库、用盒子占位、后续替换。
>
> 先把三件事分开——**这三个机制在不同层，混在一起谈会得出错误结论。**

---

## 1. 三层澄清（带代码证据）

| 层 | 在哪个代码里 | 产什么 | 建筑? |
| --- | --- | --- | --- |
| **Placemaker 内核** | `Core/`（我们要移植的） | 7 条通道：铺装面、路网、道具、宗地、区域、刷地表、地形 | **完全不产建筑**。输出只有 `PlannedZoning { A,B,C,D, ZoneId }`（`Contracts.cs:910`），四个角 + 一个区名 |
| **CS2 游戏层** | `Game/`（我们不搬） | 把 zone 变成真实楼 | **有，但用的是游戏自己的 zone 生长系统**：按地块格子数从 prefab 池里挑"能放下"的建筑 |
| **TownForge 内容层** | `src/town/modern.ts`（4,140 行） | 建筑体块 | **参数化**：从地块 bbox 算数量、进深、高度，`placeProto({kind: 'slab'})` 直接造体块。**没有任何预制体尺寸表** |

所以问题的准确答案是：

- **"Placemaker 按位置匹配预设"** —— 不成立。它在 cityskyline 仓库里连建筑都不产。
- **"同类型不同尺寸地块 → 建筑不同"** —— 成立，但**是 CS2 游戏做的事**（prefab 池 + 尺寸过滤），cityskyline 用参数化顶上了这个缺口。
- **"参数化还是固定预设"** —— 原版 CS2 是**固定预设匹配**（plus 等级升级），TownForge 是**参数化**。两条路都存在，只是不在同一层。

### 1.1 为什么当初会用参数化顶上

因为搬不过来：CS2 的建筑 prefab 是带完整模型的资产包（几万个），加上 zone 生长逻辑依赖 ECS。参数化是从地块形状直接算出体量，不需要资产——**这是妥协，不是更好的设计**。

代价也很明确：`modern.ts` 里的建筑只有 `slab / podium / tower` 几种原型 + `wallBrick / wallConcrete / roofLight` 几种材质，远看是城市，近看是盒子。

### 1.2 两条路的行为差异（回答"会不会不同"）

| | 固定预设匹配（CS2 原版） | 参数化（TownForge 现状） |
| --- | --- | --- |
| 同类型、不同大小地块 | 挑**不同尺寸的 prefab**；池里没有合适的就不长楼（空地） | 同一套规则算出**不同体量**，永远能填满 |
| 尺寸离散度 | 离散（8 m 格 × 1~6 格） | 连续 |
| 细节 | 真实模型（窗户、屋顶、雨棚） | 只有体块 + 材质 |
| 缺资产时的表现 | **空地**（很显眼） | 永远有楼（不显眼但假） |
| 稀有尺寸怎么办 | 池里没有 → 不长；或长个小的留缝 | 拉伸到合适 |

**关键结论：匹配机制的软肋是"离散资产 × 连续地块"，必然出现填不满或放不下的情况。** 这正是盒子占位能补上的地方。

## 2. 你的方案可行，而且比纯参数化更合适现状

提议：**先做资产库 → 匹配 → 盒子占位 → 后续替换模型**。

我的判断：可行，并且应该在它上面加一个分层，把"几何"和"外观"彻底分开——否则替换模型时会动到几何，压楼检测、地面一致性全部要重算。

### 2.1 核心分层：Slot（建筑位） / Skin（外观）

```
zoning.quad ──按 8 m 模数切──▶ BuildingSlot（几何契约，确定性）
                                     │
                                     ├── Skin = box（占位，任何尺寸都能拉伸）
                                     ├── Skin = prefab（资产库里的固定模型）
                                     └── Skin = parametric（参数化体块，兜底）
```

**规则：Slot 决定一切几何判定（占地、退线、压楼、zoning 覆盖）；Skin 只负责"长什么样"。**

这样替换模型时：Slot 一个不动，只换 Skin。压楼检测、B1–B8 验收结果全部保持有效。这是这套方案能"渐进完善"的根本原因。

### 2.2 盒子为什么是关键一环（不是权宜之计）

- 盒子可以**拉伸到任意尺寸** → 永远不会出现"池里没这个尺寸所以空着"
- 盒子的 footprint 就是 Slot 的 footprint → 后续换 prefab 时，只要 prefab 的占地 ≤ Slot，就不会破几何
- 盒子便宜 → 24 块地几百栋楼也能实时跑，用于早期验证

**所以顺序应该是：盒子先铺满全城 → prefab 逐个替换 → 换不上的地方盒子兜底。** 永远没有"缺资产导致场景空一块"的状态。

## 3. 数据契约

### 3.1 Slot

```ts
interface BuildingSlot {
  id: string;
  kind: ZoneKind;          // 11 类，见《建筑预设规范》§2
  /** 沿街方向（与所临街道切向平行），弧度 */
  yaw: number;
  /** 面宽 × 进深，米，均为 8 的整数倍 */
  width: number;
  depth: number;
  /** footprint 四角，逆时针，米（= 定向四边形，直接可当 obstacle 回传） */
  quad: [Vec2, Vec2, Vec2, Vec2];
  /** 所属 zoning 的 id，用于回溯与验收 */
  zoningRef: string;
  /** 沿街第几排（0 = 临街），进深方向第几进 */
  row: number;
  bay: number;
}
```

`width` / `depth` 必须是 8 的整数倍——因为它们是按 8 m 宗地格切出来的（`ZoneGuard.cs:56`）。这条是硬约束，也是 prefab 匹配的钥匙。

### 3.2 Skin 资产

```ts
interface BuildingAsset {
  id: string;
  kind: ZoneKind;
  /** 占地，米，8 m 模数 */
  footprint: { w: number; d: number };
  /** 层数与总高（米） */
  floors: number;
  height: number;
  style: string;          // 中式 / 现代 / 工业 …
  /** 只给离散匹配用：能否被拉伸（盒子 = true，prefab = false） */
  stretchable: boolean;
  /** 模型资源键；box 时为空 */
  meshKey?: string;
}
```

### 3.3 切分规则（zoning.quad → slots）

1. 认准临街边（`RoadAlongEdge` 的 `RingSegment`）
2. 沿街方向切成 `width` 段（8/16/24/32/48，按 zone kind 的预设面宽）
3. 进深方向 1..6 格，按 zone kind 的预设进深
4. 剩余不足一格的边角料：**不硬塞**，留给地面（绿地/铺装）。硬塞的结果是出现一堆 3 m × 5 m 的畸形楼
5. 每块 slot ≥ 一个 8×8 格

**四条被 31 块真实宗地逼出来的修正**（原规则在真实几何上会碎）：

| 情况 | 原规则 | 改成 | 依据 |
| --- | --- | --- | --- |
| 宗地比目标面宽还窄（实测最窄 8.56 m，目标 16 m） | 照样放一块 16 m 的楼 | 放**有多少用多少**的一块，标为补位块（`moduleWidth=false`） | 否则越界 7.4 m，并和左右邻宗地的楼重叠 |
| 宗地比 1 格还窄（实测 6.00 m） | 放一块 6 m 的楼 | **不切**，整块留作地面 | 6 m < 1 格，进 3D 一眼假 |
| 单排宗地进深 14 m（余量 ≥ 半格） | 按格取整 → 8 m 楼，白扔 6 m | 直接用 14 m，标 `depthFilled` | 后面没有第二排要跟它对齐，留 4 m 后院只是白扔地（浪费 46.9% → 14.3%） |
| 深宗地进深 17 / 25 / 33 m | 按格取整 → 16 / 24 / 32 m | **保持不变**（1 m 后院合理，多排要对齐） | 多排之间要共用院墙，行高必须一致 |

> 关键教训：**"进深必是 8 的整倍"这个前提是错的**。真实宗地进深实测
> 17.00 / 25.00 / 33.00 / 14.00 / 22.00 / 12.75 / 8.50，全都不是 8 的倍数
> （台账 D-019）。早先的结论来自我们自己造的合成用例——那种用例太干净了。

## 4. 匹配算法

### 4.1 三层回退（这是"永远填满"的保证）

```
for each slot:
  1) prefab 精确匹配   footprint 完全相等（8m 模数内），且 kind 一致
  2) prefab 包含匹配   prefab.footprint ≤ slot，差值 ≥ 一格 → 留退线或补硬质
  3) box 拉伸          按 slot 尺寸拉伸，高度按 kind 的层数区间
```

评分（第 1、2 层内部排序）：

| 项 | 权重 | 说明 |
| --- | --- | --- |
| 面宽差 | 3 | 沿街立面最重要，差一格就错缝 |
| 进深差 | 2 | 进深不足会漏出后场 |
| 高度匹配度 | 1 | 与容积率反解的层数比较 |
| 风格一致 | 1 | 同一街区优先同风格 |

### 4.2 同类型不同大小，会不同吗

会，而且是**我们控制的**：

- 池里有 8×16 / 16×16 / 24×16 三种低密商业，8 宽的地块拿 8×16、24 宽拿 24×16
- 池里只有 16×16，遇到 24 宽地块 → 走第 2 层：放一个 16×16 + 侧面补 8 m 硬质（或放两个 8×16 拼排）
- 池里空的 → 第 3 层盒子，尺寸正确但没细节

**所以"不同大小长不同楼"是自然结果，但要显式配「变体」**：同一 kind 至少要有 2~3 种尺寸变体，否则 24 宽的地块永远只能拼两个小的，立面节奏会碎。

### 4.3 真实楼位到底有多大（实测，不是估计）

4 份真实方案、31 块宗地切出 **39 个楼位**（全部 `commercialLow`），宽×深组合只有 11 种：

| 宽×深 | 个数 | 说明 |
| --- | --- | --- |
| 16.0 × 16.0 | 14 | 主力档，占 36% |
| 14.0 × 14.0 | 8 | **非 8 m 模数**（D-019 的"单排铺满"） |
| 16.0 × 8.0 | 5 | 沿街单排、进深只有一格 |
| 16.0 × 12.8 | 2 | |
| 12.8 × 24.0 | 2 | |
| 9.0 × 12.8 | 2 | |
| 9.0 × 8.0 | 2 | |
| 8.6 × 16.0 / 11.0 × 16.0 / 16.0 × 14.0 / 14.0 × 16.0 | 各 1 | |

**分布结论（推翻了早先"面宽 6~22 m"的说法）**：楼位面宽实际只在 **8.6~16 m**，中位数 16；
进深 8~24 m，中位数 14。两头极值（6 m / 22 m）在这批真实数据里**没有出现过**。

由此得到的阶梯原则 —— **按模数补，不要按样本枚举**：

| 做法 | 问题 |
| --- | --- |
| 把 11 种组合全做成资产 | 对着 4 份方案过拟合；下一批数据一来又缺 |
| 只补 8 m 模数的整数倍（8/16/24/32 宽 × 8/16/24 深） | ✅ 精确匹配吃住 16×16 / 16×8；非模数（14 / 12.8 / 9 / 8.6）交给第 2、3 层回退 |
| 靠"包含匹配"硬吃所有尺寸 | 立面节奏会碎（同 §4.2） |

**已补一档 `shop-16x8`**（原库没有，5 个真实楼位全部掉到兜底）。补齐后预制件命中率：

| 方案 | 楼位 | 预制件 | 命中率 |
| --- | --- | --- | --- |
| stripMall | 12 | 12 | 100% |
| outdoorMall | 13 | 7 | 54% |
| mallPark | 5 | 2 | 40% |
| shopsPark | 10 | 1 | 10% |
| **合计** | **40** | **22** | **55%** |

剩下 45% 全部是**非模数尺寸**（14 / 12.8 / 9 / 8.6），走"包含匹配 → 盒子拉伸"兜底，
所以 E5「楼位全覆盖」仍然是 100% —— 这正是 Q-012 定的口径：**先把盒子铺满，再谈像不像**。

> 注意上表合计 40 而不是 39：batch 的切分口径与本文档 §4.3 开头那次统计（39）差 1 个，
> 原因是两处对 `frontDir` 的取值不同（batch 用真实贴合点方向，统计脚本用最近街道端点）。
> 差 1 个不影响分布结论，但**统计口径要写清楚**，否则下次会当成回归。

## 5. 三阶段落地

| 阶段 | 做什么 | 验收 |
| --- | --- | --- |
| **E1 · Slot 层（1 周）** | zoning → slots 切分 + 盒子 skin + 3D 渲染 | 全城楼位铺满，无重叠、无越界；B1–B7 全过 |
| **E2 · 资产库（1~2 周）** | 11 kind × 2~3 尺寸变体 ≈ 30 个资产；先用简化几何（盒子 + 屋顶 + 材质） | 匹配率（1、2 层命中）≥ 85%；剩余走盒子 |
| **E3 · 模型替换（持续）** | 逐个资产换成真实模型；`meshKey` 从空到有 | 换资产后 Slot 与压楼检测结果**逐位不变** |

E3 的验收标准写死在这里：**换模型不许动几何**。这是整套方案的正确性标志。

## 6. 对我们原计划的影响

| 原计划 | 调整 |
| --- | --- |
| 《B · 建筑预设规范》§3.2 的 11 类预设 | 保留为 **Slot 的尺寸规则**（进深/面宽/层数），不再直接当"建筑" |
| 建筑由 PCG 的「容积率反解层数」算高度 | 改为：容积率 → 目标层数 → **用于给 slot 与 skin 打分**，不再直接决定单栋楼高度 |
| D-001「建筑留在 TS 侧」 | 细化为：**Slot 切分在 TS，Skin 可插拔**（box / prefab / parametric） |
| 资产系统 D-002「用合成资产表」 | 正好变成这套资产库的雏形：`{id, footprint, height, style, meshKey}` |

## 7. 验收（E 组，与 `packages/slots/src/validate.ts` 一一对应）

| 编号 | 指标 | 阈值 | 说明 |
| --- | --- | --- | --- |
| E1 | slot 尺寸对 8 m 模数偏差 | 进深 ≤ 0.05 m，或 `depthFilled`（单排铺满） | 面宽允许补位块，单独计数（D-019） |
| E2 | slot 两两重叠 | 0 对 | 同一宗地内用局部框解析判；**跨宗地不比**（frame 不同，见 D-021） |
| E3 | slot 落在宗地四边形内 | 越界 0 | 必须传原始 `zoning.quad`，不传就明写"跳过"，不假装通过 |
| E4 | 边角料比例 | ≤ 30% | |
| E5 | 楼位全覆盖（每个 slot 都有外观） | 100% | 预制件覆盖率写进摘要，是**阶段 E2** 的进度指标，不参与判定（Q-012） |
| E6 | 畸形块（任一方向 < 1 格） | 0 个 | |
| E7 | 换 Skin 后几何指纹 | 逐位不变 | `fingerprint()` 对 slot 数量 + quad 坐标取哈希 |

| outdoorMall | 8 块 1992 m² | 13 个 1921 m² | ✓ | ✓ 0 | ✓ 0 | ✓ 3.6% | ✓ 13/13 | ✓ 0 |
| shopsPark | 12 块 2352 m² | 10 个 2016 m² | ✓ | ✓ 0 | ✓ 0 | ✓ 14.3% | ✓ 10/10 | ✓ 0 |
| stripMall | 6 块 3341 m² | 12 个 3072 m² | ✓ | ✓ 0 | ✓ 0 | ✓ 8.1% | ✓ 12/12 | ✓ 0 |
