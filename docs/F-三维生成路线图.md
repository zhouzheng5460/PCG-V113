# F · 三维生成这条路怎么走

> 起因（用户原话）："现在的规则验证还是太抽象了，我看不明白。"
>
> 这句话是对的，而且问题不在界面做得丑 —— 在**看的东西不对**。规则验证器回答的是
> "这条街合不合规"，而人想知道的是"这块地会长成什么样"。这是两个问题。

---

## 0. 一句话结论

**已经跑通了一个能看、能选、能改的三维查看器（不是 PPT，是真渲染）。** 它把 Placemaker 的四个几何通道
经 `SceneIR` 立起来，54 份真实方案可切换，改一栋楼的层数只重建那一个节点。
它离"PCG 那样的三维生成工具"**只差资产替换一级**了 —— 楼还是盒子。

### 1.1 它长什么样

- **mallPark**：5 栋楼、37 条街道、300 个物件（树/家具/车位线），宗地虚线框可见
- **shopsPark**：10 栋楼沿一条弧形园路排开，一目了然"楼是沿街长的"
- **park**：129 棵树 + 步道网，但**地面 0 块** —— 引擎真的没给草地底（台账 Q-008）
- **parking**：593 个物件，车位线成排、行道树成列

最后两条特别值得说：这两件事**在 2D 验证器里看不出来**，在三维里一眼就看到。
三维不是"更好看的截图"，它是**另一类证据**。

F3 之后还多了一类证据：**增量**。选中一栋楼拖滑块改层数，右栏"本次更新"显示
`新建 1 · 复用 114 · 删 1 · 2.2 ms` —— 如果哪天它变成 `新建 115`，说明增量层被某处绕过了，
这比看画面快得多。

### 1.2 原型暴露出的真问题（都已记账）

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| 页面全白 + `SyntaxError` | `String.replace(p, s)` 会把 s 里的 `$'`、`$&` 当特殊标记展开，three 源码里真有这种序列，于是整份文档被插进了脚本中间 | 静态内容一律改成函数式替换 `replace(p, () => s)`；`editor-web/standalone.mjs` 同一个坑一并修 |
| 楼顶死黑、侧面正常 | 在 (x,z) 里逆时针的多边形，按右手法则法线朝 **−Y**。第一版直接把三角化结果当顶面用，顶面朝下了 | `prism` / `flatRing` / `ribbon` 三处绕序全部反向；不反向的话是**静默翻面**，不报错只是黑 |
| 截图拿到一片背景色 | 页面只在"画面变了"时渲染；WebGL 缓冲区合成后可能已清空，此时截图就是空的 | 截图前调 `renderNow()` 强制重绘一帧（真实用户不受影响，看的是合成结果） |
| `Identifier '_m1$1' has already been declared` | three 的 core 与 module 两个产物各自有同名内部辅助变量，拼进同一作用域就炸 | core / module 各包一层 IIFE，用 `__CORE` / `__MOD` 命名空间合并，re-export 由 `Object.assign` 天然覆盖 |
| 量高误差稳定在 21% | 正交下"1 米 = 多少像素"对**竖直方向**不是 `画布高 / (2×视野半高)`，还要乘 `cos(仰角)`；等轴 38° 时竖直方向被压到 0.788 倍 | 不写解析式，改成**在该楼的屏幕位置现场标定 1 m 竖直线占多少像素**。还顺带让透视视图的数字不会偷偷偏掉 |
| 换视图后画面缩成一条 | 五个预设共用一个 `viewSize`，那是按等轴算的；正视下地块 120 m 长、9 m 高，同一个 `viewSize` 就浪费掉 90% 竖向空间 | 切预设时把包围盒 8 个角投到相机空间，按 `max(高, 宽/aspect)` 重配视野（`stage.fitToView`） |
| 拖了滑块"没反应"（0 次重建） | 覆盖表的 key 用了楼位 id（`z0-b0-r0`），而查询用的是节点 id（`bld:z0-b0-r0`）—— 两边口径不同，覆盖永远查不到 | 统一成**节点 id**：编辑回路拿到的选中态本来就是节点 id，改成同一个口径（台账 D-026） |
| 楼高读出 0.44% 误差 | 楼块 `y1` 写成 `h + ELEV.marking`，而 `y0` 是 `ELEV.marking - 0.02`，于是几何比标注高 **2 cm** | 改成 `y1 = y0 + h`，误差回到 2e-6%。**注意：门禁没拦住它**（0.44% < 2% 阈值），是"数字跟上一轮的 2e-6% 一比不对"才发现的 → 见下面那条教训（D-027） |

## 2. 三种"三维"不是一回事

这是本文件最重要的一张表。混着说会导致"做完后发现不是想要的"。
**F3 之后 L1 与 L2 已经并成一套了** —— 有 SceneIR、能选中、能改、增量刷新，只是楼还是盒子。

| | L1+L2（**已有**） | L3 真模型（缺） |
| --- | --- | --- |
| 输入 | Plan IR → **SceneIR**（带几何指纹） | SceneIR + 资产库 |
| 楼是什么 | quad 挤出到 `层数 × 层高`，每栋是**可选中的节点** | 真实 prefab（屋顶、窗、雨棚） |
| 能做什么 | 看 + 选 + 改层数 + **增量刷新**（改 1 栋只重建 1 个节点） | 看 + 选 + 改 + 替换外观 |
| 不能做什么 | 楼还是盒子；改不了街道与宗地（那是编辑器的活，不是查看器的） | — |
| 对应 PCG 的 | `core/sceneIR` + `editor/three/realizer.ts` | 资产库（docs/E） |

**先做 L1 是对的，但不能停在 L1。** L1 是只读快照，每次切方案整场重建；
变成工具需要的是"改一处只动一处"，那是 L2 的增量层，也就是 `geomKey` 比对。
这一步在 F3 补上了：`packages/scene-ir`（纯数据 + 指纹）+ `view3d/src/realizer.ts`（按指纹增量）。

## 3. 架构：SceneIR 已经插进来了

参考实现是 PCG 的 `vendor/pcg-editor-src`（`core/sceneIR.ts` + `editor/three/realizer.ts`）。

```
        F3 之前                          F3 之后（现在）
  Plan IR ──► three 对象图      Plan IR ──► SceneIR ──► three 对象图
              (一次性重建)                    (按 geomKey 增量 patch)
```

`realizer` 那三条纪律，照抄，一条没改：

1. **只吃 SceneIR**，不读 Plan、不读生成规则 —— 语义与渲染彻底解耦。
   落地证据：`view3d/src/app.ts` 里现在**一行图元代码都没有**。
2. **换轴只在一个地方发生**。我们比 PCG 少一个坑：IR 本来就是 (x, z) 地面 + y 高度，
   和 three 一致，所以这里**根本不翻轴**。（PCG 是 (x, y) 平面，必须翻一次；翻两次就是镜像。）
3. **增量 patch**，不 clear 整个场景 —— 拖一个顶点不该让别的楼消失再出现。
   落地证据：改一栋楼的层数 = `新建 1 · 复用 114 · 删 1`。

另外两条 PCG 的选择，都采纳了：

- **主视图用正交等轴**（45° / 38°），不是透视。**量感正确**比"好看"重要 → F2 已落地。
- **切 2D 不停机不 dispose**：停 rAF，场景与相机原样保留。**未做** —— view3d 还没有 2D 视图，
  等编辑器接进来再说。这条留在 F5。

### 3.1 SceneIR 长什么样

七种图层 + 五种节点，够表达 Plan IR 的全部几何：

| 节点 | 谁用它 | 指纹（`geomKey`）含什么 |
| --- | --- | --- |
| `extrude` | 楼块、地块底板 | `y0`,`y1`,环 |
| `surface` | 铺装/草地/水面/宗地底色 | `y`,环 |
| `ribbon` | 车行道/人行道/步道/围墙 | 宽,`y`,中心线 |
| `line` | 轮廓/宗地虚线/车道中心线 | `y`,虚线?,闭合?,折线 |
| `instances` | 乔木冠/干、灌木、花池、家具、标线 | 形状,实例变换数组 |

**指纹刻意不含**：颜色、`props`（面板文字）、图层。所以改配色、改标签、切图层都不会让楼重建 ——
颜色走 material 分支，图层走增删分支。这一条是"零几何开销"的来源。

### F2 · 正交视图 + 图层语义（**已完成**）

| # | 项 | 为什么必须先做 | 落地 |
| --- | --- | --- | --- |
| 1 | 换正交相机 + 五个视图预设 | 透视下量不出楼多高，量感错了后面全是错的 | `stage.ts` 的 `PRESETS` + `setPreset`；正交/透视两套相机常驻，切换只换 `get camera()` 的返回值。切预设时 `fitToView` 重配视野 |
| 2 | 楼高层数可读 | 之前没有"它是几层"的入口 | 楼块 `userData` 带 `kind/floors/height/w/d/id`；点画布拾取（`Raycaster` + NDC，正交同样可用），右栏出"用途/层数/层高/总高/面宽×进深/楼位 id"，选中那栋加半透明黄罩 + 黄线框 |
| 3 | 街道分带 | 一条色带看不出"这是条街" | 先铺 `w+3.2 m` 浅色带（两侧各 1.6 m 人行道，y=0.10），再把车行道 `w` 盖在中间（y=0.13）；`w≥9` 才画中心线，太窄画了反而脏 |
| 4 | 树的种类 × 尺寸档 | 全是锥体像插了一地路障 | 乔木（锥+柱，按 `scale` 分档）、灌木（球）、花池（扁盒）三类各自实例化；`scale` 直接作用到高度 |
| 5 | 标线单独一层 | 和树混在一起读不出"这是画在地上的" | `LayerToggles.markings` 独立开关，只吃 `FLAT_ROLES`（车位线/箭头/decal），贴地扁片 |

**Gate（已过）**：等轴视图下量一栋楼，`geomH` vs `层数 × 层高` 误差 **2.2e-6%**，
屏幕投影 vs `geomH × 现场标定的像素/米` 误差 **6.6e-14%**（`verify.mjs` 自动断言）。
另断言：五个预设的 `preset`/`ortho`/按钮高亮三者一致；真实鼠标坐标点得中楼块；
关掉标线图层物件数 300 → 186；换方案后选中态被清、不留悬空高亮框。

### F3 · SceneIR 与增量更新（**已完成**）

这是从"查看器"变成"工具"的那一步。

| 项 | 计划 | 落地 |
| --- | --- | --- |
| `packages/scene-ir` | 节点类型带 `geomKey` | 5 种节点（extrude/surface/ribbon/line/instances）× 7 个图层；**纯数据，一个 `THREE` 都没有**（离线校验会 grep 这条） |
| `realizer` | 按 `geomKey` 比对，只有形状/高度变了才重建 | `view3d/src/realizer.ts`：`update(ir)` 返回 `{built, reused, removed, ms}`，复用路径连 `BufferGeometry` 都不碰 |
| 选中/悬停 | 只切材质，零几何开销 | 选中 = 换一份预制的自发光材质 + 翻一个 `visible` 标志（棱线几何在构建时就存好了） |
| 编辑回路 | 拖一个宗地角点 → 只换那一块 | **改成拖层数滑块**：改 1 栋楼的层数 → 只重建 1 个节点。理由见下 |

**为什么不是"拖角点"**：view3d 是按设计只读的（§6.3 明确写了"不在 L1 上做编辑"），
编辑 UI 属于编辑器，不属于查看器。但增量层要验的是**同一条代码路径**
（`配置变 → buildSceneIR → realizer.update`），所以换了个人人都能做的输入：
选中一栋楼，拖层数滑块。它比拖角点更贴题 —— **改的就是那一个节点的几何**。

**Gate（已过，`verify.mjs` + `scene-ir/verify.mjs` 双向断言）**：

| 动作 | 期望 | 实测 |
| --- | --- | --- |
| 改 1 栋楼的层数 | 只重建 1~2 个节点 | `新建 1 · 复用 114 · 删 1`，**2.2 ms** |
| 选中一栋楼 | 零几何重建 | `built/reused/removed` 三个数一动不动；材质 emissive `0xffc83d`、棱线 `visible` |
| 关一个图层（标线） | 只删那一层 | `新建 0 · 复用 114 · 删 1` |
| 恢复自动层数 | 几何回到原样 | 指纹与改之前**逐字节相同** |
| 同一方案两次打开 | 像素级/数据级一致 | `irKey` 长度 3905，两次完全相同 |
| 离线（无浏览器） | 改一栋只有 1 个节点变 | 4 份方案全部 `changed = 1` |

## 5. 数据侧要补什么

现在的画面已经把 Plan IR 榨干了。要做到 L3，缺这些：

| 缺 | 谁该给 | 影响 |
| --- | --- | --- |
| 楼块的**高度** | C# 的 zoning/建筑通道 | 现在是我按 `KIND_SPECS` 猜的（可手动覆盖，但那是人填的）；引擎真算的高度会更准 |
| `PlanObject.prefab`（资产 id） | C# 的 objects 通道 | 现在只能按 `role` 猜形状；有了 id 才能直连资产库 |
| `PlanNet` 的**分带信息** | C# 的 nets 通道 | 现在按 role 查宽度表；真实路有中央分隔、路肩 |
| 道路的**层级/高差** | terraform + 高程 | 现在全是 y=0 平铺，立交/坡道出不来 |
| 宗地的**退线** | zoning 通道 | 楼块会贴到宗地边线，真实城市有退线 |

前两条最容易补，建议**先补这两个**：改 `Emit.cs` 多导两个字段，三维立刻真实一档。

> 注：F3 的层数滑块**不是**这个字段的替代品。滑块是"人说了算"，
> 这里缺的是"引擎算了但没告诉我们"。两者在 IR 里分得很清楚：
> `props.auto` 是规则给的，`props.floors` 是生效值，`props.overridden` 标出谁改过。

## 6. 明确不做的事

1. **不做"从零建模"** —— 我们不是 Blender。所有几何都来自 Placemaker 的通道或资产库。
2. **不做光照/材质美术调优** —— 现在这套颜色只为"分辨图层"，够用就停。
3. **不做通用编辑 UI** —— F3 只开了一个口子：改**楼高层数**。改街道、改宗地角点属于编辑器，
   不属于查看器；真要做得先有"改动 → 提交 → 重算"的回路。
   反过来说：**任何一个新的编辑动作，都必须先证明它只重建受影响的节点**，才准进这个页面。
4. **不为了好看伪造数据** —— park 没有草地底就是没有，面板上写清楚（Q-008），不偷偷补一块绿。
   这一条是纪律：**三维是证据，不是效果图**。

## 7. 和 2D 规则验证器的分工

| | `packages/editor-web`（2D） | `packages/view3d`（3D） |
| --- | --- | --- |
| 回答 | 这条街合不合规？这块地引擎收不收？ | 这块地会长成什么样？ |
| 强项 | R1–R11 逐条、`ready` 与 C# 基线并排、可拖动即时结算 | 楼/路/树/宗地的空间关系一眼可见 |
| 弱项 | 抽象，要看懂规则得先懂规则 | 看不出"沿边贴合"这种判定，也数不出贴合点 |
| 共同 | 同一份 `bundle`/通道数据，零 dotnet，`file://` 可开 | 同左 |

**结论：两个都留。** 3D 不能替代 2D —— 一旦只用 3D，`ready` 判定又会变成"看起来对"。
