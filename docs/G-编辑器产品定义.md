## 0. 一句话说清这是什么

**TownForge = 张量场城市生成器 + 可编辑覆盖层 + glTF/GLB 导出。**
底层是把 [TownGeneratorOS](https://github.com/watabou/TownGeneratorOS)（Haxe/OpenFL）逐文件移植成 TypeScript，
上面加了三件事：可绘制**禁建区**、**路宽与拓扑点可编辑**、**GLB 导出**；
后来又整层替换出**现代城市模式**（张量场切块 + 道路横断面 + 标线 + 同心环用地 + 地块内容规划）。

和 Placemaker 的关系一句话：**TownForge 会造街道，Placemaker 不会。**
Placemaker 只给宗地（并默认"街道是玩家画的"），TownForge 的强项正好是"怎么把街道长出来"。
所以合并方向不是"用 Placemaker 替换 TownForge"，而是：

```
TownForge 造街道 → Placemaker 的宗地 / 楼位 / 资产规范接手"路上盖什么"
```

## 2. 一条场景，三个消费者

```ts
Scene = { surfaces[], solids[], props[], paths[] }   // src/scene/types.ts
   ├── 2D 编辑器   （src/render/*，canvas 2D，调色板 palette.css()）
   ├── 3D 预览     （src/ui/view3d.ts，three.js，palette.MAT[]）
   └── GLB 导出    （src/export/{mesh,props,glb}.ts，手写 glTF）
```

这是整个产品最重要的架构决定，必须保留：**2D / 3D / GLB 读同一份 Scene**，
`Model.revision` 每次重建 +1，两个视图据此判断要不要重建。
调色板只有一份（`src/scene/palette.ts`），所以不会出现"2D 看到的和 GLB 里不一样"。

导出分组（在 Blender / C4D / UE 里能单独选中换材质）：
`ground` / `road/{surface,sidewalk,junction,marking}` / `lot/<用途>` / `street/{avenue,furniture,lighting}`。

## 3. 和 Placemaker 的合并：换哪一层

**结论：保留 TownForge 的空间链（它比 Placemaker 强），把"地块内容"这一层换成 Placemaker 的规范。**

| 层 | 谁来做 | 理由 |
| --- | --- | --- |
| 城市轮廓 / 街区 / **路网** | **TownForge**（张量场 / 方格 / 放射） | Placemaker **不生成街道**，而它的 `ready` 依赖出入口接街。这块 TownForge 更强 |
| 道路横断面 / 路口 / 标线 | **TownForge**（`road/spec.ts` 规范表 + `markings.ts`） | 按比例推导、四层高度差避 z-fighting，已经很完整 |
| **地块用途（landuse）** | 换成 **Placemaker 的 11 类 ZoneKind** | Placemaker 的用地口径决定楼高/层高/面宽，是"算法第一性原则" |
| **地块内容（modern.ts 的规划函数）** | 换成 **zoning → slots → 资产匹配** | 楼必须与宗地尺寸一致（docs/E 尺寸阶梯 + 55% 命中率）；TownForge 现在是"摆轴对齐矩形再求交"，没有资产概念 |
| 建筑体块 | 先保留 TownForge 体块，再逐步换 prefab | 与 docs/F 的 L1→L3 路线一致 |
| 出入口 / `ready` 判定 | **Placemaker**（`CheckReady` + `Entrances.Suggest`） | C# 内核的核心判定，台账 D-022/D-023 已摸清 |
| 2D / 3D / GLB 三个消费者 | **TownForge** | 已经把"一份场景三处消费"做对了 |

**单位换算必须先解决**：TownForge 的 1 世界单位 ≈ 7 m（`road/spec.ts` 的 `u()` 负责折算），
而 Placemaker / slots 全部用米。两套坐标拼在一起之前，必须先定一个**唯一的换算点**
（建议放在"地块内容"入口处，只在那里 ×7 / ÷7），否则会出现"3 m 的人行道变成 21 m"这种静默错。

### 3.1 换进来的顺序（每步都能单独回退）

1. **只读并行**：TownForge 出街区与宗地 → 导出成 `PlanZoning[]`（米）；
   用 `packages/slots` 切楼位、算层数，结果**画在同一个 Scene 上做对照**（先不替换现有内容）。
2. **单块替换**：选中一块地，切换"内容来源：TownForge / Placemaker"，比较基底面积、层数、覆盖率。
3. **默认替换**：住宅 / 商业 / 办公默认走 Placemaker，工业与公园先留 TownForge（它们没有资产库）。
4. **接 `ready`**：出入口接街判定进流程，让"这块地引擎收不收"变成可见状态。

### 3.2 已落地：单位与桥（G2，本轮）

**单位只有一处定义**：新建 `src/core/units.ts`，`UNIT_M = 7` + `u()` / `meters()` / `sqMeters()` / `sqUnits()`。
`road/spec.ts` 从它 re-export（原来这个"全世界的尺度"居然定义在一个道路规范文件里）。
`test/bridge.test.ts` 里有一条断言：全仓 `export const UNIT_M` 只能出现一次，且必须在 `core/units.ts`。

**桥**（`src/bridge/`，只读，不改 TownForge 的几何）：

| 文件 | 职责 |
| --- | --- |
| `zone.ts` | `LandUse`(9) → `ZoneKind`(11)；`planHeight()` 把任意高度规整成「层数 × 层高」，层高取自 `KIND_SPECS` |
| `placemaker.ts` | 街区多边形 → **最小面积外接矩形**（米）→ `PlanZoning` → 我们的 `cutZoning` 切楼位；逐块回报拟合比 |

**场景出口也改了**（`scene/build.ts`）：楼高不再是"半层"的任意值，统一成 `层数 × 层高`。
于是 `heightScale`（界面上的"楼高 0.5–3×"）语义从"把楼拉高"变成"**层数倍数**"——
量出来的层高永远是真实值（3 / 4 / 4.5 m），GLB、2D、3D 三处一致。

**实测（n=10/15/24 × seed 7/42，米制）**：

| 指标 | 结果 |
| --- | --- |
| 街区 → 宗地 | 70~80 街区 → **64~67 宗地** |
| 因"太不方"跳过 | 1~5 块（**1.4%~6.3%**，逐条记账，不静默） |
| 四边形拟合（街区面积 / 外接矩形） | 中位 **88%~90%** |
| 楼位进深 | 24.5~28.6 m，**100%** 贴近 8 m 格（±4 m 内） |
| 楼位面宽 | 6~60 m，全部落在 `KIND_SPECS` 的目标面宽附近 |
| 楼高 | 全部 = 层数 × 层高；n=15 的 425 栋里层高 3 m 285 栋 / 4 m 71 栋 / 4.5 m 69 栋 |
| 我们的楼位数 vs TownForge 栋数 | **2.0~2.5 倍**（Placemaker 的切分更细：面宽 16~24 m 一块，TownForge 是每块地 1~3 栋大体量） |
| 层数被钳制 | 19%~49%（用途/高度档位的映射还需要调，这是下一个该优化的点） |

**两条硬约束（必须记着，别指望绕过去）**：

1. **街区不一定能被四边形表达**。张量场切出三角形/楔形街区，外接矩形拟合只有 41%~50%。
   硬套会把楼排到隔壁街区的土地上，而 Placemaker 那边没有任何机制能发现"这个宗地是假的"。
   所以低于 `MIN_FIT_RATIO = 0.6` 的街区**不产宗地**，只记账（台账 D-034）。
2. **楼位数量会明显变多**（2~2.5 倍）。同一条街上，TownForge 是 2 栋大体量，Placemaker 是 4~5 个 16 m 面宽的小楼位。
   换内容来源时城市肌理会变，这不是 bug，是两套规则的口径差；要在面板上让人看得见（下一步）。

**验收**：`node node_modules/tsx/dist/cli.mjs test/bridge.test.ts` → **104 项断言 0 失败**；
原有 53 次生成回归 **0 失败**（`test/gen.test.ts`）。

### 3.3 已落地：内容来源可切换（G3，本轮）

右栏新增「内容来源」一段，三档：**TownForge / Placemaker / 并排**。
它只影响**组装场景**（`buildScene(contentSource)`），不改模型 —— 切换不重跑 Voronoi、不重切街区，是即时的。

| 档 | 场景里有什么 | 实测（n=15, seed=682063530） |
| --- | --- | --- |
| TownForge | 只有 `ModernWard` 排的楼 | **396 栋**（塔 33 / 板 72 / 沿街 42 / 独立住宅 226 / 厂房 23） |
| Placemaker | 只有 `packages/slots` 的楼位 | **886 个**（全部 `kind: slot`），TownForge 的楼清零 |
| 并排 | 两套都在，左栏「Placemaker 楼位」可单独开关 | **1282 = 396 + 886**，比值 **2.24×** |

三层联动都做了：
- 左栏多一行「Placemaker 楼位」并带计数（切到 Placemaker 时自动打开该图层，切回自动关）；
- 2D 里楼位用**青色描边**（填充色和 TownForge 的楼都是灰的，光看色块分不出谁是谁）；
- GLB 导出按 `lot/placemaker/<用途>` 分组，看不见的图层不进 GLB。

**桥的两个口径修正**（都是"看着对、数字不对"的那种）：

1. **宗地不是整个街区，是沿街的进深带**。第一版把整块街区当成一个宗地扔给 `cutZoning`，
   楼位铺满街区（覆盖 85~91%），城市变成一张灰地毯。改成：按街区外接矩形的四条边各推一条
   `maxDepth` 深的带（长度两端各缩进半个进深，避免街角互压），街区内部留作院子。
2. **楼位 ≠ 楼**。`cutZoning` 给的是"划拨出去的地"，把它直接当楼的轮廓就必然满铺。
   按用途的覆盖率（商业 0.46 / 住宅 0.40 / 工业 0.50，取自 TownForge 自己的 `cover`）
   把楼位向中心收 `√cover` 倍，于是**覆盖率 37%~41%**，和 TownForge 一个量级 —— 对照才有意义。

**验收**：`node packages/editor-townforge/verify-content.mjs` → **13 项断言 0 失败**
（三档的栋数、并排 = 两套之和、比值 1.5~4×、面板按钮接线、左栏计数、零报错）；
`test/bridge.test.ts` → **110 项 0 失败**（含新增的"覆盖率 25%~65%"断言）。

### 3.4 三处修正（用户核对后）

**① 模式开关放到「城市」级**。内容来源是**整城属性**，和 预设/规模/布局/种子 同级；
原来单开一段是错的（它比"地块切分"更高一层）。读数（宗地/楼位/拟合/进深/楼高 + 本块）挪到
「地块切分」段末尾 —— 开关在城级、读数在切分口径下。

**② 去掉"旧模式内容"与 PM 内容的重叠**。只换"楼"不够：TF 的地块里还有按**它自己楼位**撒的东西
（车位线、停车场沥青、内部路、园路、围栏、车）。PM 模式下按用途分两类处理：

| 地块类型 | PM 模式下的场地 | 为什么 |
| --- | --- | --- |
| 有楼的地块（cbd/商业/住宅/公共/工业） | **清成"地面 + 绿化 + 街道家具"**：去掉标线、停车场地、内部路、园路、围栏、车 | 楼位会压在 TF 的车位上，或楼中间横着一条 TF 的内部路 |
| 不排楼的地块（parking / park / green / reserved） | **原样保留** | 这些正是 PM **还没有**对应规则的产出（见 ③），清掉就变成空地 |

**③ 停车场 / 公园的迁移对账（用户指定优先验）**。`test/bridge-parking.test.ts`（16 项断言）：

| 项 | TownForge 实测 | Placemaker 口径 | 结论 |
| --- | --- | --- | --- |
| 小型车位 | **2.52 × 5.04 m**（`CAR_STALL` 0.36×0.72 单位） | 2.5 × 5.0 m | **已合规，尺寸不用迁移** |
| 车位通道 | **6.30 m** | driveAisle ≥ 5.5 m | 合规 |
| 货车位 | 7.0 × 18.2 m，通道 16.8 m | 规范 3.5 × 18 m 级 | 合规 |
| parking 地块产出 | 630 车位 / 690 条车位线 / 7 块沥青 / 98 棵树（6 块地） | `ParkingLayer` 需**出入口接街**才 ready | **PM 暂不能接管**：桥里还没有 `access` |
| park 地块产出 | 30 块草地底 / 194 棵树 / 7 块地 | `ParkLayer` **不出草地底**（台账 Q-008） | **PM 暂不能接管**：会变空地 |
| green 地块产出 | 138 块草地 / 1222 棵树（52 块地） | 无对应生成器（绿地是规划产物） | 保留 TF |

**结论：这两类现在不适合换成 PM 生成。** 保留 TownForge 的地面与车位，
等 G5 补完「parking 的出入口接街」与「park 的草地底」再换。
这次对账直接改回了实现：过滤规则从"一刀切"改成"按用途"（D-038）。

**还没做的（用户第 2 问的剩余部分）**：
- 地块的 `density / far / heightRange` 三个参数**还没有接到桥上**。现在桥的层数是"实测楼高 → 反推 ZoneKind → 套 KIND_SPECS"，
  是**间接**的；应当让面板上的三个值直接进 `planHeight` 与宗地划分。
- 街道**不需要重画**：桥输出 `nets`（米，带 TF 实际宽度 28/20/10.5 与 PM 名义 17/12 的差额记录）。
  PM 的 `NET_WIDTH` 是 CS2 路型宽度，按它重画会把 28 m 主干道改成 17 m、街区直接散架。
- **不需要重新生成**：内容来源只换"组装"，街区/路网/地块几何全不动，切换是即时的。
  真要让 PM 自己切宗地（而不是用外接矩形推条带），才需要重生成 —— 那是 G5。

### 3.5 建筑压路：修了什么（D-039/040/041）

用户截图看到"楼压在道路上"，根因是**矩形近似连坐两次**：先拿街区外接矩形当街区，再拿它的边当楼位基线。

修正后：**沿街区自己的长边推进深带** → 带的**裁剪**交给布尔运算 → 楼的 footprint 再**裁到街区里**（和 TownForge
"先摆后裁"同一套，README §4.3）。现在每栋楼都保证 100% 在街区内，`test/bridge.test.ts` 有专门断言
（6 个规模×种子组合，0 栋越界）。

同时修掉两个连带缺陷：
- 去重同向边时误用了 `Math.abs(dot)`，把**对边**也去掉了 → 每块地只出 2~3 条带、覆盖率掉到 20%（D-040）；
- `buildRight()` 早于 URL 参数解析，导致"画面是 PM、面板亮着 TF"；顺带把 `contentSource` 写进快照（D-041）。

**当前实测**：楼位 504~846 个（自排 250~712，比值 **1.7~2.4×**）、楼位覆盖率 **27%~34%**、
楼高全部 = 层数×层高、街道 704 条 / 13.8 km（米制，带 PM 路型标签）。

### 3.8 层数改由规划参数算（不再"实测楼高反推"）

之前层数是 `round(实测楼高 / 层高)` —— 循环论证：楼高本来就是排出来的。
现在改成**参数驱动**：

```
层数 = clamp( round( min( byFar, byHeight ) ), KIND_SPECS[kind].floors )
       byFar    = far × 宗地面积 ÷ 基底面积      // 容积率允许盖几层
       byHeight = heightRange[1] ÷ 层高          // 限高允许盖几层
```

**参数来源**（`bridge/zone.ts` 的 `USE_PLAN`，照抄 TownForge 的 `PARCEL_STYLE`，高度 ×7 换成米）：

| 用途 | 密度 | 容积率 | 高度区间 | 算出来的层数 |
| --- | --- | --- | --- | --- |
| cbd | 42% | 4.20 | 22.4 ~ 49 m | **10 层**（40 m，容积率封顶） |
| residential | 40% | 2.40 | 14.7 ~ 25.2 m | **6 层**（18 m） |
| commercial | 46% | 1.84 | 11.9 ~ 21 m | **4 层**（18 m） |
| civic | 40% | 1.60 | 10.5 ~ 20.3 m | **4 层**（16 m） |
| industrial | 50% | 1.00 | 8.4 ~ 16.8 m | **2 层**（16 m，层高 8 m） |

**三个刻意的取舍**：

1. **容积率按"宗地面积"算，不按整块街区**。我们只在沿街进深带里开发（约为街区的 30%~65%），
   拿整个街区当分母会把层数抬到用途区间之外（实测 50% 的宗地被夹）。街区级口径比宗地级小 0.6~0.7 倍。
2. **`far` 由 `density × 层数` 反推**。容积率、密度、层数三者本来就满足 `far ≈ density × floors`，
   先固定两个再算第三个才自洽；顺带得到"同一用途层数稳定、地块大小只改变栋数"这个好性质。
3. **`COVER` 必须与 `USE_PLAN.density` 对齐**（都是同一组数）。不一致时 `层数 = far / COVER` 会偏 —— CBD 实测从 10 层变 12 层。

**实测**（6 个规模×种子组合，`test/bridge.test.ts` 新增 5 条断言）：
层数全部落在 `KIND_SPECS` 区间内、`实际容积率 ≈ 规划容积率（±10%）`、**同用途层数完全一致**、
`CBD 层数 > 住宅层数`；被夹的宗地占比 **0%**（改之前 43%~60%）。

**面板**：选中地块后「Placemaker 口径」会显示 `本块 低密度商业 · 4F · 18 m` / `密度 46% / 容积率 1.84` /
`实际容积率 1.84 容积率封顶`。3D 里能直接看出中心是 10 层塔楼、外围 2~4 层的层次。

### 3.11 宗地改按 C# 的 `ZoneGrid` 格子划（不再"沿街推带"）

这是 C# 规则复现里最后一块结构性差异，已按 `ZoneGuard.cs` + `ZoneBlockPredictor.cs` 原样移植。

**流程**（`bridge/zonegrid.ts`）：

```
道路（A→D，米） → ZoneBlockPredictor：两侧各切若干 block（8 m 格 × 6 排深，每块 ≤10 格）
                → 每格求格心（ZoneUtils 公式） → 格心落在哪个街区就归哪个
                → 贪心最大矩形（C# 的 ZonedRect） → 每条矩形 = 一个 PlanZoning（米）
```

**照抄的常量与公式**：

| 项 | 值 | 出处 |
| --- | --- | --- |
| 格边长 | **8 m** | `ZoneGuard.Cell` |
| 块深 | **6 排 = 48 m** | `Size.y = 6` |
| 每块格数 | ≤ **10** 格（超出按块切） | `chunks` |
| 格宽（离路多远） | `ceil(路宽/8 - 0.01)` 格 | `CellWidth` |
| 格心 | `Position + d·(sy-2y-1)·4 + Right(d)·(sx-2x-1)·4` | `CellCentre` |
| 矩形 | `CellRect(x0,x1,y0,y1)` | `CellRect` |
| 自由端外扩 | `半格宽 - 1 格` | `Side` 的 `ext` |

**关键的一处"不是照抄"**：C# 用 `CellVisible` 把"弯曲路段两侧重叠格子"里输的那格藏掉；
我们没有那面旗，改成**按面积判重**（8 m 桶的空间哈希 + 点在旋转方块内）。只比格心不行 —— 见 D-048。

**实测（替换前后对比）**：

| 指标 | 推带（旧） | **格子（新）** |
| --- | --- | --- |
| 宗地数（n=15 / n=24） | 64 / 67 | **78 / 72** |
| 因形状跳过 | 1~5 块 | **0 块** |
| 楼位进深中位 | 25.2 m | **18.8 / 19.0 m** |
| 进深落在 8 m 整格 | 43%~53%（"贴近"100%） | **98% / 96%（精确整格）** |
| 楼位覆盖率 | 27%~34% | **35% / 36%** |
| 楼位数（vs TF 396 / 712） | 650（1.6×） | **1301 / 1774（3.3× / 2.5×）** |
| 拟合比（街区 / 格网覆盖） | 0.88~0.90 | **0.99** |

**两个必须说清的后果**：

1. **"跳过楔形街区"的问题消失了**。格子是道路自己带出来的，再怪的街区都有格子落在里面，
   所以 `skippedByShape` 从 1~5 变成 **0**（D-034 的限制被这条替代）。
2. **楼会更多更小**（3.3× / 2.5×）。这是 CS2 式划区的真实后果：整块地被 8 m 格铺满，
   一栋楼只占一格或几格。TownForge 是"每块地 1~3 栋大体量"，两者是两种城市肌理 ——
   不是 bug，但要让人在面板上看得见（下一刀：把"楼位/栋"的比值作为读数亮出来）。

**验收**：`test/bridge.test.ts` 新增两条 —— **宗地边长都是 8 m 的倍数**、**进深 ≤ 6 格（48 m）**；
全套 **152 项断言 0 失败**，access 29 / parking 29 / park 22 全绿。

### 3.12 资产槽位 + 高楼退台（"楼位/栋"变成可见读数）

两件事一起做的：把 **楼位 / 自排 = 3.3×** 这个数摆到面板上，同时把**资产槽位**这套机制立起来。

**① 读数**（右栏「Placemaker 口径」）：

| 行 | 值（n=15） |
| --- | --- |
| 楼位 / 自排 | `1301 / 396 栋 · **3.3×**` |
| 资产槽位 | `注册 0 · 命中 0% · 拆塔楼 195` |

面板里跟一句解释：CS2 式划区把整块地铺满 8 m 格，一栋楼只占一格或几格；
TownForge 是每块地 1~3 栋大体量 —— **同一个街区，两种肌理，不是 bug**。
这个数不给出来的话，用户看到"楼变多 3 倍"第一反应是"是不是算错了"。

**② 资产槽位机制**（`bridge/assets.ts`，docs/E 的"先有槽再填模型"）：

```
楼位 → assetKey = `用途 | 面宽×进深(米) | 层数`
     → 注册表命中？用预制件 : 用程序化 prefab（盒子）
```

- key 里**必须带层数**：同样是 16×16 的地，1 层和 10 层不可能是同一个模型；
- key 里**必须带面宽×进深**：docs/E §4.3 的实测是"按尺寸档匹配"，挑错了楼会穿出地块；
- 注册表现在是**空的**（还没有真实 GLB），所以命中率 **0%** —— 这不是缺陷，是当前状态，
  面板如实写"命中 0%"。将来接模型时只改注册表，不动其它代码。

**③ 高楼退台（最省成本的一次"像楼"）**：≥8 层的楼拆成 **裙房 + 退台塔身** 两块，
塔身每边内退 12%。一块盒子永远是盒子；两块一退台就有体量关系（TownForge 的 CBD 预设也是这么做的）。
实测：n=15 有 **195/1308（15%）** 的楼位被拆，体块数 1308 → 1503（+15%）；n=24 是 8%。

**验收**：`test/bridge.test.ts` 新增三条 —— 体块数 = 楼位 + 拆分数、拆分的都是 ≥8 层、命中率在 0~1；
全套 **170 项断言 0 失败**。

### 3.13 程序化预制件：腰线 + 女儿墙 + 模数命中（"盒子"变"楼"）

用户选了"先做程序化预制件库，有真模型再换"。这一刀做的是**几何细节**，不是美术资产：

| 细节 | 做法 | 代价 |
| --- | --- | --- |
| **楼层腰线** | 每层交界处一道外挑 **3 cm** 的薄檐（水平四边形） | 只加三角形，**不加场景对象** |
| **女儿墙** | 屋面下沉 0.5 m + 一圈 0.25 m 厚的围边（外皮 + 顶面） | 同上 |
| **高楼退台** | ≥8 层拆成「裙房 + 塔身（每边内退 12%）」 | 体块 +15% |

为什么做成"加三角形"而不是"加对象"：一座城 1300 个楼位，每栋再多 4 个对象就是 5000 个节点，
2D/3D/GLB 三处都要为它们付出调度成本。而腰线/女儿墙本质是**同一个体块的表面细节**，
放进 `extrudeSolid` 的 `detail` 参数里最自然 —— 导出、预览、2D 都自动跟着走。

**"模数命中"取代了空的资产注册表**：

```
楼位的 面宽 × 进深 是否落在 8/12/16/20/24/32/40/48 m 档上（±0.6 m）
  → 是：将来能**直接**换真模型，不用拉伸
  → 否：要么按最近档拉伸，要么补一档资产
```

实测命中 **97%~100%**（1189/1105/1287/1224/1866/1774 个楼位里只有 8~45 个不在档上）——
这不是巧合：宗地是按 8 m 格划的（§3.11），`cutZoning` 又按 `KIND_SPECS` 的目标面宽切，
所以楼位天然落在模数上。**这条数据直接支撑 docs/E 的结论：资产库按模数补，不要按样本枚举。**

**验收**：`test/bridge.test.ts` 新增三条 —— 模数命中率在 0~1、命中数 ≤ 楼位数、命中率 > 5%
（防"算错了但看着像 0"）；全套 **182 项断言 0 失败**。3D 里塔楼立面能看到逐层的水平腰线。

### 3.14 密度诊断：为什么这么密？用地规则到底影响了什么？（实测）

用户问："建筑为什么这么密集，地面规则对用地的划分生效了吗？影响了建筑的位置和旋转和类型了吗？"
把数字摊开（n=15 / seed=682063530）：

| 口径 | 我们（PM 模式） | TownForge | 结论 |
| --- | --- | --- | --- |
| 宗地覆盖街区 | **92%** | — | 几乎铺满，**没有内部院子** |
| 建筑基底覆盖 | **35%** | ~40% | **面积上不密**，甚至比 TF 略低 |
| 楼位数（栋） | **1308** | 387 | **栋数密 3.4×** |
| 平均楼位 | 19 × 21 m | 每块地 1~3 栋大体量 | 每栋小了一个量级 |
| 楼位进深 | 18.8 m | — | 8 m 整格 98% |

**所以"密"不是面积密，是栋数密 —— 因为每栋变小了。**
根因两条：① 宗地按 8 m 格铺满整块街区（§3.11，C# 的 6 排深 × 四边）；② 宗地被切成 2~3 格宽，
`cutZoning` 落到"窄宗地整块补位"分支，出来就是 19 m 宽的楼。

**用地规则生效在哪、没生效在哪**（这是用户真正问的）：

| 维度 | 用地规则影响了吗 | 实测 |
| --- | --- | --- |
| **类型**（材质/层数/退台） | ✅ 影响 | 工业 2 层 / 商业 4 层 / 住宅 6 层 / CBD 10 层，材质按 kind 分 |
| **尺寸** | ⚠️ 弱 | `KIND_SPECS.targetWidth` 是 16/24/32，但实测平均 19~21 m —— 窄宗地上目标面宽被截断 |
| **栋数密度** | ❌ **不影响** | 各用途都是 **2.6~3.4 栋/千m²**，几乎一样 |
| **旋转** | ❌ 不影响 | 朝向只由**道路**决定（实测宗地方向 1~7°，跟随街道），同一块地内全同向 |
| **位置** | ⚠️ 弱 | 位置由 8 m 格网定；用途只通过 targetWidth/depth 间接影响切分 |

**结论：现在的"用地"只影响"盖什么楼"，不影响"盖几栋、盖多满"。**
这正是"地面规则没完整生效"的具体含义。

**两条让它生效的修法（可量化，待做）**：

1. **密度预算**：每块地按 `USE_PLAN.density × 街区面积` 算可建基底上限，
   按楼位顺序保留到用满，**剩下的楼位不盖楼**（留院子 / 停车 / 绿地）。
   效果：高密度用途真的更满，低密度用途真的更空 —— 密度才成为"规则"。
2. **面宽优先，窄宗地不盖**：`cutZoning` 现在对"比目标面宽窄"的宗地会整块补一栋，
   于是 19 m 的碎块全变成楼。改成：窄于目标面宽 **60%** 的宗地不盖（划成院/绿地），
   只留够宽的。效果：栋数下降、平均楼变大，且 `targetWidth` 重新有意义。

**关于旋转**：现在"所有楼都跟着街道转"是对的（真实城市的街墙就是这么形成的）。
如果将来要给背街建筑一个 ±90° 的次方向，那是**街区内部**的事，要单独设计 —— 我倾向不做，
它会破坏街道界面。

### 3.15 用地按城市形态 + 宗地按深度分带（回应"太密 / 类型重复 / 没有最小面积"）

用户三点：① 地块要最小面积、要**合并**成更大的地块，不能都靠"一次分割"；② 用地别按比重抽，
要**用满 11 类**并按城市形态分布；③ 先查 C# 文档再动手。三条都做了。

**先查到的 C# 依据**（`docs/proposals/s40.md` + `Core/Build/ZoneLots.cs` + `ZoneGuard`）：

> "the plots ARE the cells：布局先决定内容放哪儿（数量、图案、进深、出入口），
> 再把每个候选 plot 换成 ZoneGuard 会划的确切格子……**Speckled pads are ≥ 2 cells wide**
> （一格宽的 pad 会被深度规则切没）……**Cell dedupe tightened (overlap beyond 0.1 m)**"

对应到我们这边，缺的正是"**plot 规划 + 深度分带**"这一层 —— 之前是"所有格子都划"。

**① 宗地：按列深度分带，带最小面积**（`zonegrid.zoningRects` 重写）

```
每一列（沿路一格）先算自己的深度 = 从 row 0 起连续被占几格
深度相同的相邻列 → 合并成一块（C# 的 ZonedRect）
少于 minCols(2 列 = 16 m) 不划  ·  少于 minCells 不划（按用途给 4~12 格 = 256~768 m²）
```

这是 C# 的**深度规则**（`GameDepthPass` + `ReduceDepth`）。之前用的是"贪心最大矩形"，
会切出"3 列深 1 格 + 2 列深 2 格"的锯齿，每块都小、于是每块都盖一栋小楼 —— 密度就是这么来的。

**② 用地：11 类按同心环 + 主干道加成分配，并保底全覆盖**（`bridge/landuse.ts`）

| 环（q = 到中心距离/半径） | 候选 |
| --- | --- |
| q < 0.12 | `officeHigh` / `commercialHigh`（CBD） |
| < 0.3 | `commercialHigh` / `officeLow` / `mixed` / `commercialLow` |
| < 0.52 | `residentialHigh` / `residentialMedium` / `mixed` |
| < 0.72 | `residentialMedium` / `residentialRow` / `residentialLow` / `commercialLow` |
| < 0.88 | `residentialLow` / `lowRent` / `residentialRow` / `industrial` |
| 其余 | `industrial` / `lowRent` / `residentialLow` |

叠两条修正：**贴主干道的往商业/混合挪一档**；**保底补位** —— 11 类里缺哪个，就从"最贴近它该在的位置"
的街区里换一个过来（优先换掉重复最多的那类）。参数也改成按 **kind** 取（`KIND_PLAN`），
否则"低密度住宅"和"高密度住宅"会拿到同一个容积率。

**③ 实测对比（n=15 / seed=682063530）**：

| 指标 | 改之前 | **改之后** |
| --- | --- | --- |
| 用地类型数 | 6~7 类（住宅几乎全 `residentialMedium`） | **11 类全覆盖** |
| 宗地数 | 78（≈ 每街区 1.1 块，但都是小格拼的） | **73**（每街区 ≈1 块，合并出来的大块） |
| 单块宗地规模 | — | **28~120 格 = 1792~7680 m²** |
| 宗地覆盖街区 | **92%（铺满，没院子）** | **69%（有院子了）** |
| 建筑基底覆盖 | 35%~36% | **23%~29%** |
| 楼位尺寸分化 | 全是 19~21 m | **工业 24×23、联排 8×16、办公 24×26、住宅 16×13** |
| 用途栋密度 | 全部 2.6~3.4 栋/千m² | **工业 0.9~1.2 / 联排 1.3~5.2 / 办公 0.8~1.5** |

**"联排 8×16" 是关键证据**：`residentialRow` 的 `targetWidth = 8`，以前这个目标面宽在窄宗地上
永远被截断；现在宗地够宽了，8 m 的联排真的切出来了。

**验收**：`test/bridge.test.ts` 新增四条 —— **用地 11 类全覆盖**、**宗地是合并出来的**
（数量 ≤ 街区数 ×1.2）、**宗地满足最小面积/最小列宽**（≥3.5 格且 ≥15.5 m 宽）；
覆盖率带放宽到 15%~65%（这是"有院子"的表现）。全套 **194 项断言 0 失败**。

### 3.16 宗地真的合并了：移植 C# 的 `ReduceDepths`（回应"不要所有地块都是一次分割产生的"）

§3.15 交付之后，用户的原话是"**尝试合并地块形成更大面积的地块，不要所有地块都是一次分割产生的**"。
§3.15 声称已经做到了（"宗地 28~120 格 = 1792~7680 m²"），**但那是错的口径** —— 我把
`strips.length` 当成了"合并"，实测每个街区仍有 4~5 条互不相连的带子。这一轮先承认这一点，
再按用户第 ③ 条的要求**去 C# 里找规则**，而不是自己发明合并算法。

#### 3.16.1 先量清楚：碎片到底碎在哪

| 探针 | 数字（n=15 / seed=682063530） | 结论 |
| --- | --- | --- |
| 每街区含几个 grid | 中位 **9~11 个**，最多 20 个 | 一条街被切成好几段，**每段各自成块** |
| 每个 grid 贡献几列 | 132 格 ÷ 20 grid ≈ **6.6 格** | 大量 grid 只贡献 1 列 |
| 列深分布 | `{1:263, 2:100, 3:84, 4:87, 5:60, **6:1095**}` | **65% 的列是满深 6 格**，深度不是问题 |
| 面积 | p50 **1152** = p90 **1152**，max 2688 | 绝大多数就是同一尺寸的 3 格×6 格 |
| 街区主朝向占格份额 | 中位 **57%**（p10 35%），中位 4 个朝向桶 | 一块地同时被 4 个方向的路切 |

**结论**：不是"深度不对"，也不是"没合并"，而是**提取算法本身在切碎**——
一道剖面里**一个浅列就能把满深带拦腰截断**，`[6,6,4,6,6]` 会被切成 `[6,6]`+`[4]`+`[6,6]`，
而 `minCols=2` 还会把中间那段直接丢掉。

#### 3.16.2 找到的 C# 规则（这次是"原样移植"，不是启发式）

`Core/Build/ZoneGuard.cs:1231` 的 `ReduceDepths`，注释写明是**移植自游戏 `Game.Zones.CellOverlapJobs`
（反编译 1.6.2f1）**：

> after the cells are blocked, **every block evens out its column depths**. Walking from both ends at
> once, column x becomes CalculateLeftDepth(x) (and CalculateRightDepth from the other end) and
> ReduceDepth blocks every cell from that depth on. A column deeper than both neighbours is cut to the
> deeper neighbour unless a neighbour of its own depth stands beside it, so a lone 1-column cutout
> (depth 2 between blocked columns of depth 0) is blocked entirely ...
> **Neighbour blocks of the same road continue the row (GetDepth past the end of the block).**

两条要点，正好是缺的那两块：

1. **游戏是"削平"，不是"切开"** —— 深的列让到跟邻居一样浅。削平之后剖面是平滑阶梯，
   等深段自然变长，地块就大了。这不是我发明的合并规则，是 C# 里就有的。
2. **`Get` 越界去读同一条路相邻块的排号** —— 同一条街被 `chunks` 切成几段时，
   靠它把排号接起来，两段的深度才一致，**才有东西可并**。

同时补了另外两个 C# 下限（都是原文档里的字）：

| 规则 | 出处 | 我们怎么用 |
| --- | --- | --- |
| 宽 ≥ 2 格（16 m） | `Core/Layers/Common/StreetShops.cs:317` "Two cells wide at least: the game blocks a lone column of cells" | `filterRects` 的 `minCols` |
| 深 ≥ 2 格（16 m） | `Core/Build/ZoneGuard.cs:71` `public const int MinRows = 2;` | `filterRects` 的 `minRows` |
| 面积下限按用途 | 我们自己的规划表（工业大、住宅小） | `MIN_CELLS` 4~12 格 = 256~768 m² |

#### 3.16.3 改了什么

| 文件 | 改动 |
| --- | --- |
| `bridge/zonegrid.ts` | **新增 `reduceDepths`**（C# `ReduceDepths` 逐行移植，含 `Left`/`Right`/跨块 `Get`）；`gridDepth` 提成函数；`zoningRects` 接受削平后的深度并**取 min(自身, 削平)**（削平生效，且绝不越界到别的街区）；提取换成**取满的最大同深矩形 + 逐层剥**（`peelRects`）；**新增 `mergeRects`**（共线 + 同深 + 相接 → 并成一块）、**`filterRects`**（三个下限，**放在合并之后**） |
| `bridge/placemaker.ts` | 全局跑一次 `reduceDepths`（它要跨块读邻居）；宗地流水线改成 `zoningRects → mergeRects → filterRects`；**格子归属排序提成 `ClaimPolicy` 参数**（6 种，实测选优）；新增 `parcelAreaMedM2 / parcelAreaMaxM2 / parcelAreaCv / rectsRaw / rectsMerged / rectsFinal / composedShare / parcelCoverShare` 八个读数 |

**一个必须记住的坑（D-054）**：合并时不能用"世界坐标投影取平均"。
两个相邻 grid 的朝向最多差 0.8°（`dot > 0.9999`），在离原点 1 km 处就是 **14 m** 的假偏移——
既判不准"贴不贴"，还会把边长算成 40.33 m。**一律换到 a 的局部坐标系里量，并按 b 自己的整格宽度外扩。**

#### 3.16.4 格子归属排序是密度参数（6 种策略实测）

一块街区会被 9~20 个 grid 同时覆盖，8 m 方格只能归一家，所以"谁先拿"直接决定地块形状。
这个顺序以前埋在代码里（D-049 就吃过一次亏），现在提成显式参数并**留了四组实测数字**：

| 策略 | 条带 | p50 | p90 | max | CV | 楼位 | 楼栋占地 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `order` 生成顺序 | 353 | 1152 | 1152 | 3215 | 0.33 | 1315 | 28% |
| `y` 排号优先（离自己那条路最近） | 412 | 538 | 845 | 1998 | 0.43 | 950 | 19% |
| `long-y` 长 grid 优先，再排号 | 343 | 730 | 1459 | 4843 | 0.80 | 1106 | 24% |
| **`long` 沿路格数多优先（采用）** | **317** | 1152 | **1536** | **4843** | **0.62** | 1242 | 28% |
| `atomic` 整块 grid 原子占位 | 223 | 1152 | 1613 | 4685 | 0.43 | 1014 | 23% |
| `atomic-fill` 原子 + 逐格补空 | 318 | 1152 | 1536 | 4621 | 0.58 | 1196 | 27% |

（5 个种子的均值，`n=15`。）

短 grid 先抢门口，把长边整条带咬碎（这正好解释了 D-049 当时的直觉为什么是错的）。

#### 3.16.6 这一轮**没有**解决的问题（写在前面，免得下次又以为搞定了）

1. **楼位总数只从 1364 降到 1300（-5%）**。原因已定位：楼位数 ≈ `宗地面积 × 密度 ÷ (面宽 × 进深)`，
   而 `KIND_SPECS` 的面宽/进深是 docs/B §3.2 定死的（住宅 16~24 m、联排 8 m），
   所以**宗地变大只是让每个宗地多塞几个楼位，不减少楼位总数**。
   要真降下来只有一条路：**`cutZoning` 按名义 `depth` 落楼、余深留作后院**，
   而不是按 `maxDepth` 把整块地折成 2~3 排（见 D-056）。
2. **街区内部仍然"从街到背铺满"**。实测楼位离车行道平均 17.9~23.3 m，
   分布是 `≤12 m 29% · 12-24 m 48% · 24-36 m 19% · 36-48 m 4%` ——
   也就是 48 m 进深的地块被 3 排楼铺满，没有后院/内院。这就是"看起来太密"最直接的来源。

### 3.17 ~~界面重构成「粗规划工具」~~ **已撤回**（2026-11-03）

> **撤回原因**：改完之后实际用起来问题比原来更多（左右职责虽然分开了，但"改的是哪一层"仍然要靠猜，
> 且新增的片区/留白区概念与既有参数面板互相打架）。用户要求**回到首版 UI**，本节仅作记录，不再生效。

以下为原内容（已废弃）：

用户的产品定位很明确：这**不是**专业城市规划软件，也不是逐条路 / 逐个地块的参数编辑器，
而是"给已有自定义建筑快速生成合理城市配套"的工具。所以信息架构从**参数调试器**改成**城市粗规划工具**。

#### 3.17.1 新的三层信息架构

```
左栏（表达意图）            中栏（地图）              右栏（当前选中对象的属性）
├ 城市范围   规模/留白      ├ 工具条：选择 / 绘制区域 / 绘制留白区   ├ 城市
├ 城市结构   4 个粗控       ├ 片区整体高亮（点任一块地 = 选中它所属片区）├ 片区
├ 功能分布   6 类用途        └ 图例（颜色 = 用途）                  ├ 地块
├ 留白区     绘制/清除/处理方式                                     └ 留白区
├ 风格与预览 高度档位/楼高缩放                        底部：重新生成 · 局部刷新
└ 底部主操作
右栏底部「高级设置」（默认收起）= 原来所有算法参数 + 图层显隐
```

#### 3.17.2 每个粗控都映射到真实参数（没有空滑杆）

| 粗控 | 真实作用 |
| --- | --- |
| 城市规模 小型/中型/大型/超大型 | `nPatches` = 10/15/24/40 |
| 道路密度 低/中/高 | `parcelPitchM` 34/26/20 + `parcelTargetA` 90/60/40 |
| 建筑密度 低/中/高 | `building.spacingM` 18/12/8 + `maxPerParcel` 2/3/5 |
| 绿地比例 低/中/高 | 按 6%/12%/22% 把地块用途覆盖为 `park`（写进 `patchEdits`，不覆盖用户已指定的） |
| 城市方向感 弱/中/强 | 街网形态 `field` / `tensor` / `grid` |
| 功能分布 6 类 | 把选中片区所有地块的 `use` 覆盖成该用途 |
| 建筑高度 四档 | `BUILDING_PRESETS.apply`；`mixed` 不动任何值 |
| 留白区 | 复用模型里已有的 `zones`（blocked 地块） |

**为什么没有"城市边界绘制"**：模型的 `withinCity` 是按到中心的距离算的（`grid.ts:458`），
不是用户画的多边形。加一个画了不生效的边界工具就是撒谎，所以先不提供，改用「留白区」做局部排除。

#### 3.17.3 片区（District）

模型里没有"片区"概念，是界面上按 **k-means（k=4，固定初值）** 把地块聚成 4 团：

- 初值取"按坐标排序后等距四个地块"，**不引入随机数** —— 同一座城两次打开必须是同样的 A/B/C/D，
  否则"改片区 A"会指向不同的地块。
- 编号按质心 x 再 y 排序，A 永远是最西边那片。
- 点任一块地 → 右栏自动切到「片区」并整片高亮（`view2d.setDistrict`，画在地块填充之后）。

#### 3.17.4 长说明改成问号

原来面板里大段"文档式"说明（"街区先按沿街面宽切成一排临街地块……"）全部换成 `?` 悬停提示。
判据：**用户不需要理解算法**。

#### 3.17.5 已知未做（诚实记账）

1. **局部刷新仍是整城重算**。真正的片区增量需要模型支持"只重建某片区的 ward"，
   那是核心生成流程的改动；本轮约束是不改 PCG 算法，所以按钮上写明了"当前为整城重算"。
2. **绘制区域（框选）** 目前只切到矩形绘制模式，框选后自动指定用途还没接。

   没有强制改成规范里那六色 —— 换色会同时影响 3D，留到下一轮和 GLB 一起改。
